# Demo decision

Written 2026-10-27, after the leakage audit ([evidence/leakage_audit/REPORT.md](../evidence/leakage_audit/REPORT.md)). Every number below comes from a saved run record; the table is generated by `tools/fresh_attempts_summary.py` (`evidence/demo_decision/fresh_attempts.json`) and `tools/run_trace.py`.

## Decision

**Primary demo: "PUA - AdFind.EXE Execution", run live, with source handling set to leakage-controlled.** The report is the Joeware AdFind page, read by Tavily; the model is Nemotron 3 Super on Token Factory; the evaluator is a Token Factory Sandbox.

**Repair evidence: the saved run `demo/replay/pua-adfind-exe-execution.json`** (fresh attempt 1 below), shown as a *recorded* run and labelled as one. It is a real write, test, diagnose, repair, retest sequence under leakage-controlled inputs: attempt 1 was a valid rule that missed the attack file; the repair prompt carried the missed events; attempt 2 detected the attack with 0 benign events on the development logs and 0 on the held-out logs.

**Honest-failure clip: "PUA - Suspicious ActiveDirectory Enumeration Via AdFind.EXE", fresh run 1** (`demo/replay/pua-suspicious-activedirectory-enumeration-via-adfind-exe.json`): the best rule detected the attack but matched 350 benign events on the development logs (858 on the held-out logs), so it is shown as not passing.

## Why this scenario

| Candidate | Leakage-controlled runs | Passed | Notes |
|---|---|---|---|
| AdFind Execution | 6 | **6 of 6** | all with 0 held-out benign events; two passed on the first attempt, two after repairing a miss, one after a miss and an invalid rule, one after two invalid rules |
| AdFind Enumeration | 4 | 3 of 4 | the failure matched hundreds of benign events; two of the passes needed an invalid-rule repair |

AdFind Execution is the one whose result can be explained in 30 seconds and whose rules do not look like the reference: in all six runs the generated rule shared exactly one detection value with SigmaHQ's rule (`AdFind.exe`, the tool the scenario is named for) out of 9 reference values, and never used the reference's hashes (checked by script on E0 to E5). A pass rate of 6 of 6 is still a small sample on one scenario and is not a reliability claim.

## Source handling in the approved runs

- `research.screening` in each record lists every retrieved page with URL, retrieval time, decision and reasons. In the Execution runs five pages were excluded: the target rule's GitHub file, sigmaquery.com, two detection.fyi pages and one page titled like the rule.
- Pages that stayed (Splunk's AdFind analytic, a Fortinet rule page, a ManageEngine page) are not pages for the target rule. **The ManageEngine page is a vendor rule page for the sibling rule "PUA - Suspicious ActiveDirectory Enumeration Via AdFind.EXE" (SigmaHQ lists it as `related: similar`).** It is not the target, the screen keeps it by design, and no run copied from it (1 of 9 reference values shared), but a stricter evaluation would exclude sibling-rule pages too. Say so if asked.
- The AdFind Enumeration runs had low-quality corroboration (mapquest.com, rocketreach.co appeared in the kept results), which is a property of the search, not a screening error.

## Known weaknesses of the demo (say them, do not hide them)

1. **After a repair the pass is not independent.** The repair prompt shows the events of the attack file the first rule missed, so a repaired rule detecting that same file is not a held-out result. The held-out benign result is the clean measurement.
2. One attack sample per scenario; lab logs; two AdFind scenarios only. 6 of 6 is not a success rate.
3. A live run takes 146 to 311 seconds in these runs. The video must say when it is cut or sped up (see the script).
4. The recorded Execution run (E1) used the earlier extraction of the Joeware page; Tavily's extraction of a page can change between days, so a recording cannot be reproduced byte for byte.
