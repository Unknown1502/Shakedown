# Rubric scorecard (internal readiness assessment)

This is a conservative self-assessment against the four equally weighted criteria in the rules (each scored 1 to 5 by judges, after a pass/fail fit check). It is **not** a prediction of the judges' scores and says nothing about other entries. The ranges are how much I would defend with the evidence in this repository.

| Criterion | Self-assessment | Strongest evidence | Highest-risk weakness | Concrete fix | Fix done? | Remaining uncertainty |
|---|---|---|---|---|---|---|
| **Technological Implementation** (how well it is built; how effectively it uses Token Factory and an NVIDIA model) | 3.5 to 4 | Nemotron 3 Super is called through Token Factory in extraction, generation and repair; every candidate runs in a Token Factory Sandbox (offline microVM); a bounded repair loop with real SigmaHQ ground truth; 244 tests; a container built from the repository passed 23 of 23 acceptance checks including a live run; a leakage audit that found and fixed real defects | The demo's repair shown is from a recorded run, and a live run may pass on attempt 1 and show no repair; the benchmark input is easier than a real report | Show the live run and a clearly labelled recorded repair (script does this); state the benchmark limits (done) | Yes (script, docs) | Whether judges value the audit work; whether they run the live demo and it is up |
| **Design** (a complete, coherent product, not a proof of concept) | 3 to 4 | One page: live first, replay clearly labelled, attempt strip, diff, test evidence, results with denominators, the source-handling line, exportable evidence, honest failures (red and hatched cells) | Nobody outside the project has used it; a live run takes 2.5 to 5 minutes; plain visual design | A first-time-user test; progress is shown per attempt | The user test is not done (I cannot); progress shown | Judges' first impression of a long wait |
| **Potential Impact** (a credible, specific case for a real problem and audience) | 3 | The problem is concrete (valid-looking rules that miss attacks); the evidence is measured (6 to 7 of 20 first attempts, 14 of 20 after repair, expert 20 of 20; zero to two benign events on held-out logs) | The data is lab data, one sample per rule, and the expert rules win; there are no users or adoption figures and none are claimed | Say exactly that; position as automating the path to a tested candidate, not as better rules | Yes | Whether a real SOC would value it more than the numbers suggest |
| **Quality of the Idea** (creative, non-obvious use; understanding of the problem space) | 3 to 4 | Treating a generated rule as a candidate that needs execution evidence, with grounded extraction (verbatim quotes), a held-out benign set, honest failure reporting, and a self-audit of benchmark leakage | AI-generated Sigma rules and evaluation loops are not new in general, and it is not claimed to be | Describe the differentiator as the integration and the evidence discipline | Yes | Whether the leakage audit reads as rigour or as a distraction |

Tavily bonus: the integration is a functional runtime call on every live run (one extract, one search), the sources are kept with provenance and the screen decisions are recorded; its value to the rule is **not shown** (the ablation could not separate the arms). Do not claim it improves rules.
