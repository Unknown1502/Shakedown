# Evaluation methodology (pre-registered)

Written 2026-10-27 before the first batch run. Anything changed after seeing results is listed under "Deviations" at the bottom.

## Question
When given only a descriptive threat-report-style text, does a Nemotron-driven build-test-repair loop produce Sigma rules that detect the described attack and stay quiet on benign Windows logs, compared with the model's first attempt and with SigmaHQ's expert rule?

## Tasks
- Source: the 470 usable SigmaHQ rule/EVTX pairs in `docs/DATASET_AUDIT.md`.
- **Sample of 20**, drawn with `random.Random(20261027)`: 14 `process_creation`, 3 `ps_script`, 3 `registry_set`. The 20 are written to `evaluation/tasks.json` before any model call.
- **Task input** = rule title + description + references + ATT&CK tags. The expert rule's detection logic and its attack sample are never in the prompt. Task inputs are SigmaHQ metadata, not independently written threat reports; they are often more explicit than real reports (see Limitations).

## Configurations (same tasks, same fixtures, same scorer)
1. **One-shot**: the first candidate only (iteration 0). If invalid, it counts as not detecting.
2. **Repair loop**: best candidate after at most 3 repairs. The best is chosen by deterministic score: attack detected first, then fewer benign events.
3. **Expert**: the SigmaHQ rule itself, evaluated by the same code.

Model: `nvidia/nemotron-3-super-120b-a12b` through Token Factory, temperature 0.

## Fixtures and splits
- **Attack**: the rule's own SigmaHQ regression sample (one EVTX file). **Unit = attack file (scenario).** Detected means at least one event in the file matched.
- **Benign development** (the repair loop sees its hits): evtx-baseline `win7-x86`, 129 EVTX files.
- **Benign held-out** (never shown to the model): evtx-baseline `win10-client`, 352 EVTX files.
- **Unit for benign** = number of matching events, plus the number of rules with at least one hit.

## Metrics, with denominators
- Validity: candidates passing `sigma check` / candidates produced.
- Attack detection: tasks where the attack file was detected / 20.
- Benign false positives: rules with at least one hit / 20, and total matching events.
- Repair success: tasks where iteration 0 failed acceptance and a later candidate passed / tasks where iteration 0 failed.
- Cost and time: total tokens and wall-clock per task.
- All also reported for the 2026-dated subset separately.

**Acceptance criteria** (used by the loop to stop): attack file detected AND zero benign events on the development baseline.

## Known threats to validity (stated in advance)
- **One attack sample per rule.** The repair loop sees events from a *missed* attack file, so post-repair detection of that same file is *not* a held-out result. Only one-shot detection, and benign false positives on `win10-client`, are clean. Generalisation of repaired rules to other attack variants is **not measured**.
- **Training-data contamination** is possible: SigmaHQ rules are public. We cannot show the model has not seen them. The 2026-dated subset is small and does not remove the risk.
- **Small and lab-generated data.** Results describe these fixtures only, not real-world detection performance.
- **n = 20.** Rates carry wide uncertainty; no significance claims are made.
- The expert rule is not designed to be tuned against these exact baselines.

## Deviations
- The frozen sample contains **0** rules dated 2026 (checked after freezing, before any model call), so the planned "2026-dated subset" cannot be reported from this batch. The sample was not re-drawn. A separate, later run on the 41 rules dated 2026 would be needed for that claim.
- Debug runs with `--limit N` are not reported as results.
- **Run 1 (`batch_20261026_194636.json`) had 5 of 20 tasks abort** because the repair loop crashed when the evaluator could not parse a model-written rule that `sigma check` had accepted ("invalid definition"). That is a loop bug, found after seeing results. The loop was changed to record such a candidate as unloadable and send the evaluator's error back for repair (`tests/test_loop.py::test_rule_the_evaluator_cannot_load_is_repaired_not_a_crash`). **Run 2 reruns all 20 frozen tasks with the fixed loop**; both runs are kept and Run 1 is reported alongside. No other change was made between runs. Nothing about the tasks, fixtures, metrics or acceptance criteria changed.
- **Run 2 analysis motivated a method change.** Of the 19 completed Run-2 tasks, the validation failures were 12 "rule must contain at least one condition", 6 YAML syntax errors and 1 bad log source, i.e. file-structure mistakes, not detection logic. **Run 3 (`--rule-format structured`, the new default)** changes three things together: (a) the model returns JSON fields and code renders the YAML; (b) the generation prompt lists standard Sigma field names for the task's log source; (c) the client retries transient server errors (HTTP 429/5xx/529; Run 2 lost one task to a 529). Same 20 frozen tasks, fixtures, metrics and acceptance criteria. Runs 1 and 2 stay in the results as the free-form-YAML baseline. Because (a) and (b) changed together, Run 3 cannot say which of them helped.
- **Run 3 did not help, and the Run 2 diagnosis was wrong.** Run 3: first candidate valid 10/20; 26 of the 64 candidates were empty skeletons (`"groups": []`, `"condition": ""`) that rendering rejected. The structure was never the main problem: Nemotron Super returned an empty rule under the strict schema. A small side experiment (4 failing tasks x 2 trials per setting, 8 trials each, scratch script not kept in the repo) found: current settings 3/8 empty; 16k token budget 5/8 empty; plain `json_object` mode 4/8 empty; **thinking turned off (`chat_template_kwargs: {"enable_thinking": false}`) 0/8 empty**, using about 190 completion tokens instead of about 1000. **Run 4 = Run 3 with generation thinking off** (`--thinking off`; spec extraction is unchanged). Same 20 frozen tasks and metrics. The 8-trial experiment is small, so Run 4 is the real test, and rule quality with thinking off is unknown until it runs. Runs 1-3 stay in the results.
- **Run 4 result (`batch_20261027_064430.json`): thinking off made rules valid more often but worse at detection.** First candidate passed `sigma check` 16/20 (Run 3: 10/20), but attack detected after repair only 7/20 (Run 3: 11/20), and 13 of 20 tasks exhausted the repair budget, many repeating the same undetecting rule four times. So thinking helps rule quality and also causes the empty skeletons. **Run 5 = thinking on (default) + resampling:** an empty skeleton (`groups` empty or `condition` blank) is treated as a failed call, not a candidate, and the same prompt is resampled up to 3 times without spending a repair attempt (`max_resamples=3`; the extra tokens are counted). Structured output and field hints stay on. Same 20 frozen tasks and metrics. This is the last method change planned before final reporting; every run stays in the results table.
- **Sandboxes access arrived on 2026-10-27 (afternoon IST); Run 6 = Run 5's configuration evaluated inside a Nebius Token Factory Sandbox.** Runs 1-5 used the local isolated Docker runner. Before switching, `tools/sandbox_parity.py` ran 30 seeded-random SigmaHQ reference rules through both evaluators on the rule's attack file and on the `win7-x86` benign logs: attack and benign match counts agreed on 30 of 30 (`data/audit/sandbox_parity.json`). Parity on 30 rules is evidence, not proof, for the other rules. **Run 6 changes only the evaluator** (model, prompts, thinking on, resampling, structured output, the 20 frozen tasks, metrics and acceptance criteria are those of Run 5). It is the run the submission headlines because it is the evaluator the shipped product uses. That choice was made before Run 6 started and **Run 6 is reported whatever it shows**. Runs 1-5 stay in the table. Because Nemotron's output is non-deterministic even at temperature 0 (the difference between Runs 3 and 5 on the same tasks shows how much), Run 6 vs Run 5 differences are mostly noise and are not a finding about the evaluator.
- **Sandbox base image.** The Sandbox importer returned HTTP 404 for the digest-pinned Debian reference the local runner uses, so the Sandbox image's Debian base was imported by tag (`debian:bookworm-slim`) on 2026-10-27. The evaluation image is immutable by UUID (`data/audit/sandbox_image.json`); the checker and the benign archives inside it were verified against the release's SHA256SUMS before upload.
- **Demo recordings were redone on the Sandbox** (`demo/recorded/`); the earlier local-runner recordings are kept in `demo/recorded_local/`. Outcomes changed between the two sets (Copy From VolumeShadowCopy passed locally in 2 attempts and failed here; AdFind failed locally and passed here in 2). That is the model's run-to-run variance, not an evaluator difference, and both sets are kept.
- **Pre-registration of the confirmatory evaluation (written 2026-10-27, before any model call on the new tasks).** The 20 tasks of `evaluation/tasks.json` were used for six runs while the method changed, so they are a **development set**; method choices after Run 1 were made looking at them. To get a number that is not tuned to them:
  - `tools/select_confirmatory.py` froze **20 different tasks** (`evaluation/tasks_confirmatory.json`, seed 20261028; none shared with the development set): **10 dated 2026** (pool of 31) and **10 older** (pool of 345), from `process_creation`, `ps_script` and `registry_set`. Rules dated 2026 are more likely to postdate the model's training data, which also lets us report the 2026 subset separately.
  - **Change under test (the only one):** if the model still returns an empty rule skeleton after the 3 resamples, make one last call with thinking off (`fallback_without_thinking`, `--fallback-thinking-off`). Rationale: in the Run 6 results 10 of 59 attempts were empty skeletons that survived all resamples, and thinking off returned 0 empty answers in 8 trials. Implemented with tests (`tests/test_loop.py`, three `test_thinking_off_fallback_*`); each attempt records `thinking_fallback`.
  - **Run 7 (development tasks, Run 6 + fallback, Sandbox)** shows the effect of the change on the tasks it was designed on. It is exploratory.
  - **Run 8 (confirmatory tasks, Run 6 configuration + fallback, Sandbox)** is the headline number. **Run 9 (confirmatory tasks, Run 6 configuration without the fallback, Sandbox)** is reported next to it as the comparison. Both are reported whatever they show, once each. No further method change will be made after seeing Runs 8 and 9; if one is made it will be listed here and Runs 8 and 9 will not be re-run to improve the number.
  - Metrics, acceptance criteria, held-out logs and the expert baseline are unchanged. The 2026 and older subsets are reported separately with their denominators.
- **Results of Runs 6 to 9 (all on the Sandbox evaluator; tables in `docs/RESULTS_TABLE.md`, generated from the saved batch files).**
  - Run 6 (development tasks): one-shot 5/20, after repair 11/20, expert 20/20, held-out false positives 0/20 rules.
  - Run 7 (development tasks, with the fallback): one-shot 6/20, after repair 12/20. The fallback was used on 11 attempts.
  - **Run 8 (confirmatory tasks, with the fallback, headline): one-shot 7/19, after repair 14/19 (14/20 counting the one errored task as a miss), expert 19/19, held-out false positives in 1 of 19 repaired rules (1 event).** One task of 20 errored: three model answers in a row had no parseable JSON and the loop did not catch that error.
  - **Run 9 (confirmatory tasks, without the fallback): one-shot 6/20, after repair 14/20, expert 20/20, held-out false positives in 1 of 20 repaired rules (2 events).**
  - **The fallback made no measurable difference** (14/20 in both confirmatory runs; 12/20 against 11/20 on the development tasks). We keep it on in the shipped configuration because it is what Run 8 measured and it costs nothing when it is not needed, but we do not claim it helps. The 2026-dated subset (10 tasks) behaved like the older subset (after repair 7 to 8 of 10 against 6 to 7 of 10), so we have no sign that the result depends on the model having seen the rule; with 10 tasks per subset this is weak evidence either way.
  - **Post-hoc fix, not applied to Runs 8 and 9:** the loop now treats an answer with no JSON as an empty answer (resample, then the fallback) instead of raising (`NoJSONError`, `tests/test_loop.py::test_an_answer_with_no_json_is_resampled_not_a_crash`). Runs 8 and 9 were not re-run; Run 8 is reported with that task as a miss.
  - Run 8 ran at the same time as Run 7 and shared the Token Factory rate limits; this affects latency, not the measured outcomes.
- **Benchmark leakage audit (2026-10-27, after Runs 1 to 9; full report in `evidence/leakage_audit/REPORT.md`).** A live run on a SigmaHQ-derived scenario showed that web research can hand the model the rule it is asked to write. The audit found:
  - **Runs 1 to 9 are not affected by web research.** `tools/run_batch.py` makes no Tavily call; the task input is the rule title, description, references and ATT&CK tags (`scenario_report_text`). The frozen development and confirmatory definitions, tasks and results are unchanged and nothing was re-run.
  - **One incidental channel did reach the benchmark: repair feedback named the missed attack file.** SigmaHQ names each attack sample after its rule id, and `shakedown/loop.py` printed those names to the model after a missed first attempt. The id is an opaque UUID and carries no detection logic (the rule title, which is in every task input, is a far stronger lookup key), so the effect is judged small, but it was a benchmark identifier in the prompt. It affects only repairs (the first attempt is clean) and Runs 1 to 9 all had it. **From now on the feedback says "attack sample N"** (`tests/test_loop.py::test_repair_feedback_does_not_reveal_which_rule_an_attack_file_belongs_to`). Runs 1 to 9 are reported as run; they were not re-run (the pre-registration forbids re-running them to improve a number).
  - **New control, not applied retroactively:** retrieved sources are screened for answer-bearing content before the model sees them (`shakedown/research.py::screen_sources`, policy `flag` or `exclude`; live runs default to `exclude`; the pipeline default is `flag`). Every source, its retrieval time, decision and reasons are stored in `research.screening` of the run record.
  - **Recorded demos made before the control (`demo/recorded/`) are kept unchanged and are labelled when served.** For "Potentially Suspicious PowerShell Child Processes", the recording's top corroborating source was the target rule's own YAML on GitHub with its detection list visible, and the generated rule contains the same child-process set. Its pass is not evidence of what Shakedown does from a report alone. Screened re-recordings are in `demo/recorded_screened/` and are exploratory (n = 1 each): PowerShell Child Processes did not pass; both AdFind scenarios still passed.
  - **Ablation on the AdFind scenario (exploratory, 18 runs, n = 3 per cell, `evidence/leakage_audit/ablation_20261027_113437.json`):** with the two mirror pages removed, rules still passed in 4 of 6 runs against 5 of 6 with them (Fisher exact p = 1.00); with no search at all, 2 of 6. No difference at this sample size can be claimed in either direction. The ablation ran before the file-name fix, so repair feedback carried the rule id in every arm; the id probe in the summary is contaminated by that channel, while the probe for the mirror hostnames is clean.
  - None of these results are merged into the confirmatory score.
- **Live demo-candidate runs (2026-10-27, after the audit; exploratory, not part of any benchmark table; `docs/DEMO_DECISION.md`).** Ten leakage-controlled runs on two AdFind scenarios, every one kept: Execution 6 of 6 passed, Enumeration 3 of 4. They used the same method as the product (answer screening on, neutral attack-file labels, the `LeakGuard`), the Sandbox evaluator and the final model settings. They are not merged into the frozen confirmatory score and are not a success rate.
- **Changes after the audit that affect new runs only:** a guard refuses model requests carrying the target rule id or attack file name; checker error text is scrubbed of attack file names; live runs read the scenario's first readable reference by default; spec extraction retries an empty answer twice more and then fails visibly (`NoJSONError`); every record carries `source_mode` and `usage`. The frozen benchmark task lists and results are untouched, and `tools/results_table.py` regenerates `docs/RESULTS_TABLE.md` with identical content (line endings aside) from `evidence/runs/`.
